# STAGE-DONE 是「轮次结束」不是「整单收工」

`session.execution.succeeded`（探针报 `STAGE-DONE`）只表示**刚结束的这一轮**交付完成——**一个会话跑到真收工之间会报很多次**。收到它的固定动作是「核屏再判」，不是推进、不是汇报。

## 核屏三看（缺一不可）

1. **屏底是否还有 `esc interrupt`** —— 有 ⇒ 它还在跑，**假终态，不许推进**。
2. **`↓ N shells`** —— 它在跑**并行后台 shell**（典型：两条不同路径的门禁复跑、多个长命令）。有它时尤其要等，因为那几条 shell 的产物还没落盘。
3. **客观物证**：`git log --oneline -1` 是否出现新提交、约定产物（报告 / 日志 / 截图）是否落盘、远端是否已收到 push。**屏底 Ready + 产物落盘 + 提交出现，三个都齐才算那一笔收工。**

## 为什么会多轮

- **我排了多笔追加裁决**：`Esc` 不打断，裁决落文件 + 一行指针排队；它做完当前轮 → 收下一条 → 再跑一轮 ⇒ 探针**按轮各报一次** `STAGE-DONE`。
- **它自己按简报分阶段**：一轮做完一个阶段（如先改后测），下一轮接着做。
- **长门禁在后台跑**：提交 / 门禁被它塞进后台 shell，主循环先空转一轮。

## 派生规则

- ⛔ **不许把「探针说交工」直接转成对辉哥的结论**——核屏是唯一凭证；报错了比报慢了贵得多。
- **撤销 / 改单才用 `Esc`**；只想追加裁决就排队，不要打断（打断会丢它当前轮的上下文）。
- **追加了动行为面的提交（门禁实现 / `scripts/**` / hook / CI）⇒ 之前的全量绿作废**，必须在**新 head** 上重跑，别拿旧 head 的绿当凭证。
- 探针寿命绑「会话存在」，不绑「一轮任务」：反复 `STAGE-DONE` 期间**不许 kill 探针**，也**不许**因为「它报过了」就退出监控。

## ⛔ `↓ N shell` 时不要发指令催：后台 shell 一完成，那一轮会自己续跑

实测两次：轮次 `succeeded` 落下、屏上留 `↓ 1 shell`（它在等自己起的全量门禁 / 长命令），
**shell 完成通知一到，TUI 自己接着把那一轮跑完**（收门禁 → 提交 → 建 PR），还会再报一次 `STAGE-DONE`。

⇒ 动作是**等**，不是催：

- `↓ N shell` 或 `esc interrupt` 任一在屏 ⇒ 继续等，别发「继续」类指令（同一条指令进队列会与它自己的续跑撞车，
  表现为同一动作做两遍）。
- 判「真收工」仍是三看齐：屏底无忙碌行 + 约定产物落盘 + **`git log` 出现新提交**。

## ⛔ kill 探针会触发守夜兜底「立刻补挂」——同锚点会变成两条

守夜 watchdog 判「该 sid 没有 watch.py 进程」就补挂一条**脱离式**（`nohup`、`ppid=1`）探针。
你刚 kill 掉旧探针、还没挂新探针的那个空窗，正好命中它的判据 ⇒ 你会同时有两条盯同一个锚点
（一条带 Hermes 投递腿、一条只有日志文件），信号重复投递会被误读成「又发生了一次」。

**处置**（替代「kill 完就以为干净了」）：

```bash
# ① 列全（含 ppid / etime，一眼分出哪条是兜底那条）
ps -eo pid,ppid,etime,command | grep '[w]atch.py' | sed 's#/Users/xiaohui/[^ ]*/#…/#g'
# ② kill 掉 ppid=1 的兜底那条，保留 Hermes 后台句柄那条（有投递腿）
# ③ 逐 pid 复核：ps -p <pid> 判存亡
```

⛔ **判探针存活只用 `ps -p <pid>`，不要用 `pgrep -f '…' / grep -c` 计数**：你自己那层 `bash -c` 包装里
就带着同样的字符串，计数会把自己算进去（实测 `grep -c` 得到 1，而探针其实已被 kill）。

⛔ **重挂 = 先 kill 旧的那条、再起新的**，不要先起新的（等于主动造出上面那两条并存的局面）。
