# 每日策展后续处理流程

## 哲学原则

c456 不是新闻媒体。策展的终极目的是 **为用户出可执行的方案**。

每条信息在纳入清单前必须通过检验：「这个信息能帮目标用户出什么方案？」

## 完整工作流

### 阶段一：客户画像（一次性）

使用 `c456-client-interview` 采访客户，输出标准画像 JSON → 使用 `c456-strategy-creator` 生成定制策展策略 → 部署 cron。

### 阶段二：Cron 自动执行（每天 7:00）

1. 采集 RSS（按客户画像定制关键词/渠道/来源优先级）
2. 精选（≤15 条，方案导向筛选）
3. 社区源热点 → 溯源到官方源
4. 逐条读原文 → 写摘要 + 价值判断 + 打法组合建议
5. 创建一条信号草稿（不公开）
6. 推送到客户对话

### 阶段三：用户回应清单后（手动）

用户从清单中挑选某条要求展开写作时：

1. **确认范围**：用户说「可以发」还是「写篇公众号文章」？前者只执行 2-7，后者加执行 8-9
2. **深度阅读原文**：重新获取全文，目标是写独立发布的 **文稿**（不是条目式摘要）
3. **扩展研究**：搜索相关背景（GitHub Star/版本号/竞品/社区反响）
4. **考虑 AISO 分发**：这篇文稿发布后，应该分发到哪个 AI APP 的引用源？
   - 豆包 → 头条号/知乎
   - 元宝 → 公众号
   - DeepSeek → 网页 SEO 优化
   - 见 `c456-strategy-creator` §7 AISO 模块
5. **按 c456-write §A 撰写信号**：使用 c456-write 结构 + c456-voice-journalist 声线 + c456-sync 格式
6. **发布信号**：`c456 signal new --body-file --description` → `c456 signal update <id> --publish`
7. **更新本地元数据**：记录 c456-id、c456-url（用 `/signals/<id>` 不是 `/intakes/<id>`）
8. **（如需要公众号版）按 c456-write §E 撰写公众号长文**：六段式结构，加入中国市场监管对应分析，保存为本地文件或直接输出给用户
9. **返回确认**：告知客户 C456 ID + 公开地址 + 公众号文章就绪

## 术语

| 词 | 指代 |
|----|------|
| **文稿** | 完整的独立公开发布的文章 |
| **条目** | 每日清单中的单条信号 |
| **信号草稿** | 合并所有条目的当天草稿（draft, 不公开） |
| **客户画像** | 标准化 JSON，包含产品/受众/目标/能力/期望 |
| **AISO** | AI Search Optimization — 让内容被豆包/元宝/DeepSeek 等 AI 引用 |

## 踩坑记录

| 坑 | 说明 |
|------|------|
| 误把信号草稿步骤从 cron 移除 | 用户纠正：「原来的创建信号草稿是对的」— cron 必须创建草稿再推清单 |
| 用户说「第5条可以单独发」时误以为是修改 cron | 实际意思是：用户从清单挑第5条，手动写深度文稿 |
| 把文稿说成「文档」 | 用户纠正：叫 **文稿** |
| 用 `c456 signal new` 后忘记 `--publish` | 新信号默认是草稿，必须 `update --publish` 才公开 |
| 截图前忘记先 `c456 browser start` | 截图必须先用浏览器实例，否则无头截图不准确 |
| 公开地址写成 `/intakes/<id>` | 信号的正确 URL 是 `/signals/<id>`、工具是 `/tools/<id>`、渠道是 `/channels/<id>` |
| `--description` 参数传了但未生效 | 可能因 CLI 版本不支持——优先在 `new` 时传，失败后用 `update --description` 补 |
| 策展内容偏技术/大方向 | 被用户纠正——c456 不是新闻媒体，策展应为「出方案」服务，方案导向筛选 |
| **问客户「要不要加这个源」** | 用户纠正：你是专家，你自己判断。技能应该是自我进化的，不是问客户怎么办 |
| **用旧策略思维重新策展** | 改完了 cron prompt 后手动跑策展，却仍然按旧思维（科技新闻+附打法建议）筛选内容。换策略要换**整套筛选逻辑**，不只是加个「打法建议」尾巴 |
| **环境：web_extract 后端不可用** | 本机 web.extract_backend 是 ddgs（仅搜索），`web_extract` 直接报「cannot extract URL content」。抓原文一律 `curl -sL -A "Mozilla/5.0…"`；被 Cloudflare 拦的源（Search Engine Land / Moz / CMI）改用 `https://r.jina.ai/<完整URL>` 代理拿 Markdown |
| **发布技能不在当前 profile** | `c456-cli` / `c456-publish` / `c456-sync` 可能未装进 profile（本会话只有 `c456-write` + `c456-curation-philosophy`）。真源在 `~/Codes/c456-com/skills/`，备份在 `~/.hermes-bak/profiles/hermes-c456/skills/`——按需读，别以为流程丢了 |
| **只用 HTTP 200 判断「已公开」** | c456 是 SPA，未发布/404 也返回 200。必须 curl 页面 HTML 后 grep 标题/正文关键词（如正文里的专有名词）确认内容真的渲染出来，或看该条是否已进公开搜索结果 |
| **素材 URL 与本地镜像对不上** | `c456 asset upload` 返回的 `previewUrl` 会被服务端重新签名（同一 asset id，路径与哈希都变）。`c456:asset/<id>` 才是稳定锚；回填本地镜像时从 `c456 intake show <id>` 取**实际生效**的 URL，别照抄 upload 的返回值 |
