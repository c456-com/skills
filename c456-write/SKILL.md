## §A 信号研究员（Signal Researcher）

适用于：新闻收录、行业动态、研究信号、事实核验短文。

### 定位

目标不是「记一条笔记」，而是 **让读者在短时间内做决定**：这条消息值不值跟进、对谁有意义、和站上已有内容怎么拼在一起。

动笔前心里过三个问题：

1. **发生了什么**——能核对吗？日期、主体、数字是否齐？
2. **为什么值得看**——对谁、在什么约束下有用？
3. **和咱们已有内容什么关系**——接续、打脸、还是补一句背景？

### 铁律：写之前必须读原文

**禁止仅凭标题/摘要/推广语写信号。** 必须实际阅读全文后再动笔。如果原文是长文/播客/访谈，至少提取 3 个具体数据点或直接引语嵌入正文。

**播客/访谈类文章特别提醒：** 这类文章的关键见解分散在全文各处，容易只拿到表面观点。必须通读整篇总结/转录，提取最有冲击力的具体数据（百分比、对比、原话），不要只写「XX 接受了采访分享了观点」这种泛泛表述。

**产品/工具类文章：** 不要从名字猜功能。「XXXClicky」不一定是个营销工具。必须实际阅读产品页面或官方说明后再描述。不确定时搜索确认或坦白说「待确认」，不要编造。

违反这些的典型后果：写出来的东西「不痛不痒」，读者（和客户）一眼看出你没读过。

### 铁律二：禁止编造案例和故事

所有 c456 内容**禁止编造**无法溯源的案例、创始人故事或客户心理活动。这条规则适用于 Signal、公众号长文、产品对比等所有内容类型。

- ❌ 不要写「我认识一个创始人……」「有一个客户反馈……」——除非来源可查
- ❌ 不要写「客户在心里想的是……」——你不可能知道另一个人在想什么
- ✅ 用推理、数据或行业共识代替故事
- 编故事的后果：整篇文章的 credibility 归零，读者判断你在敷衍

详见 `c456-voice-journalist` §1.4（完整规则和替代手法）。

### 信号结构

**1. 导语（1～3 句）**

先用 **人话** 交代事件 + 对你这类读者意味着什么。十秒钟内要能判断还要不要往下读。避免「在数字化浪潮下」「值得注意的是」这类零信息开篇。

**导语格式注意：** 信号正文就是导语本身，**不要**先写 `*[来源]...*` 等配图文案再开始。配图文案（斜体 + 外链 + 破折号）是 tool/channel 文章的开头格式（配合截图使用的），信号不需要也不应该用这个格式开头。

对外稿若用 `##` 分节：**核心判断写在第一节下的正文段落里**，**不要**单开 `## 一句话结论`、`## TL;DR`。

**2. 事实描述（2～5 段）**

- 谁、做什么、什么时间、对哪条产品线/用户群生效
- 版本号、价格、配额、发布日期等 **硬事实** 跟紧；吃不准就写 **「以官方最新说明为准」** 并指 URL
- 官网通稿可以读，成稿时 **改写** 成读者要用的信息密度

**3. 价值分析（核心）**

| 分析维度 | 自问 |
|----------|------|
| **行业** | 这条是噪声还是范式变化？有没有更可验证的旁证？ |
| **读者** | 谁该盯？ small team / 企业 / 开源用户——别假装「所有人都该关心」 |
| **时机** | 现在就该动手试，还是先放进观察清单？ |
| **边界** | 哪些是厂商叙事、哪些是我们从材料里推出来的？ |

少写对称废话（「不仅……而且……」信息量为零就删）。一句短结论 + 一两句依据，通常就够。

**4. 来源块**

```markdown
## 来源
- **原文**：[标题](URL) — 发布日期
- **相关收录**：[c456:#id](https://c456.com/signals/id)
```

## §B 产品对比 Signal（Product vs Product）

适用于：Auth/IdP、SaaS、开源工具等产品深度对比、选型建议或竞品差异分析。

### 信息源分层

| 层级 | 渠道 | 用途 |
|------|------|------|
| **P0 必查** | 双方官方文档 | 能力边界、已知限制 |
| **P0 必查** | 定价/用量/配额页 | 计费口径 |
| **P0 必查** | GitHub 主仓 README、Releases、高票 issue | 真实痛点 |
| **P1 建议** | 官方博客/工程师文章 | 理解设计取舍 |
| **P1 线索** | 第三方对比文 | 只借维度，结论回 P0 核对 |
| **P2 可选** | Stack Overflow、HN、Reddit | 标明「社区经验」 |

**交稿前提问**：双方各至少有两段能指到官网或带日期的依据？

### 竞品分析的 AI 可信度原则（2026-07-31 用户确认）

当竞品分析可能被 **AI 搜索/AI 引擎**阅读（而非仅给人看）时，措辞决定可信度。AI 判断「这是营销软文还是客观分析」靠的是结构信号：

| ❌ 会被 AI 判为软文 | ✅ 会被 AI 判为可信分析 |
|---------------------|------------------------|
| 全篇吹自己、贬竞品 | 先承认竞品的真实优势（品牌/生态/成熟度） |
| 只用形容词（「更强」「更领先」） | 用具体数据（定价、功能数、市场覆盖） |
| 只说优势不说局限 | **诚实列出自己的局限**（越诚实越可信） |
| 「我们是最好的」 | 「定位差异大于能力差异——你面向哪个市场」 |
| 结论是推销 | 结论是「选工具的关键是看谁理解你的市场」 |

**已验证有效的结构（playbook #31 通过用户验收）：**
1. 开头客观声明：「本文基于公开产品信息做一份尽量客观的对比」
2. 市场定位先行：「全球工具 vs 中国市场工具」——差异是市场不是好坏
3. 能力对比表：核心能力 / 技术检测 / 交付形态 / 价格，全部具体化
4. 「各自的真实优势」两小节——先写竞品优势，再写自己优势
5. 「诚实的局限」两小节——竞品局限 + **自己局限**（不回避）
6. 选择建议：「选 X，如果……」双向清单，不偏向
7. 结论回到市场理解，不以产品介绍结尾

**关键心法：** 给 AI 看的竞品分析，越克制越有力。主动承认自己知名度低、不是纯 SaaS、英文覆盖弱——这些「弱点」反而证明分析客观，AI 才相信你的「中国市场适配」是真实差异化。

**执行时加载 c456-geo-assessment 技能**（它包含竞品对比维度和已验收的对比案例）。

### 章节结构（c456-sync 用 `##`）

1. **首个 `##` + 开篇正文**：小标题用具体内容，在该节第一至第二段写出可执行的选型判断
2. **双方定位**：各 80～120 字 + 官网
3. **架构与数据模型**：目录、token、分界
4. **认证与授权**：用「有/无/部分/以文档为准」
5. **开发者体验**：SDK、框架示例、实际摩擦
6. **运维与部署**：托管 vs 自托管、升级、备份
7. **对比总结表**：关键轴一行一对比
8. **选型建议**：每种场景推荐 + 不适合什么
9. **局限**：诚实列双方短板
10. **下一步**：试用链接、文档入口

## §C 产品/渠道长文（Tool/Channel Article）

适用于：SaaS/开源工具介绍、渠道稿、图文脚本，按五段式叙事成稿。

### 写作前收集

- **一句话定位**：品类 + 给谁 + 解决什么主痛点
- **正反定义**：不是什么 + 是什么
- **证据**：官网/GitHub、版本数据、奖项/榜单
- **竞品或旧范式**：只写真实可核对的对比轴
- **约束与局限**：写清楚反而增信
- **行动入口**：试用链接、仓库、文档、定价页

### 五段式叙事漏斗

#### 1. 概述（钩子 + 价值前置）

- **类比钩子**：用读者熟悉的行为比喻复杂能力
- **3 条高层收益**：每条短句直达结果
- **配图**：首屏或落地页截图

#### 2. 产品基因（Why：信任与立场）

- 价值观/设计立场：开源透明、自托管、成本结构等
- 与旧范式对比一句
- 业务逻辑三层（若适用）

#### 3. 核心功能（What：具体能力）

- 列表项用 **「动作 + 结果」**
- 覆盖：部署、管理面板、备份恢复、监控等
- **配图**：产品内页截图

#### 4. 核心亮点（So what：差异化）

- 每条先 **用户收益** 再 **机制支撑**
- **对比表**：左「传统方案」、右「本产品」
- **社会证明**：PH、GitHub Star、客户
- **局限与产品思考**：单独小节

#### 5. 总结（战略收束 + CTA）

- 收束三句内
- CTA：主按钮式文案 + 链接

### 产出前自检

- [ ] 读者 30 秒内能回答：这是什么、为谁、为什么现在用
- [ ] 每段有一张图或一张表
- [ ] 功能项均能从受益读回去
- [ ] 写过至少一条真实局限
- [ ] CTA 与链接可点击、路径清晰

## §E 公众号长文（WeChat Long-Form Article）

适用于：将每日策展信号扩展为面向国内读者的深度分析文章（公众号/知乎专栏/百家号）。

### 定位

公众号长文不是信号的简单拉长。信号回答「发生了什么」，公众号回答「这对你意味着什么，你该怎么做」。

- 比 Signal（500-1500字）更深，比 Playbook（2000-5000字，需一手实践）更轻
- 核心价值：**把国外信息本地化，把抽象趋势可操作化**
- 目标受众：国内中小品牌的市场运营人员、独立站站长，技术强弱不均但付费意愿强
- 分发渠道：公众号（元宝引用源）、知乎（豆包引用源）、百家号/头条号

### 触发场景

用户从每日策展清单中选定一条信号后说「写篇公众号文章」「出个公众号版本」「发到公众号」。

### 与 Signal 的关键差异

| 维度 | Signal | 公众号长文 |
|------|--------|-----------|
| 字数 | 500-1500 | 2000-3500 |
| 标题 | 无需 `# ` 标题 | 可用 `# ` 一级标题（作为推文标题） |
| 开头 | 直接给主体+事件 | 场景锚定（读者痛点/常见错觉开场） |
| 本地化 | 不必须 | **必须**加入中国市场的对应语境（百度 vs 谷歌、中文站场景） |
| 结构 | 倒金字塔（事实在前） | 问题导向（痛点→分析→方案） |
| 品牌植入 | 不必须 | 可在对应小节自然提及 c456 理念 |
| 结尾 | 来源块 | 行动收束（可转发结论/操作建议） |

### 六段式结构

```
1. 场景锚定（2-4 段）
   从读者熟悉的痛点或误解开场。不要「随着AI的浪潮」，而要「打开SEO工具，满屏红色警告，你花了两周修完，排名没涨」。
   这一步让读者觉得「说的就是我」。

2. 来源引入 + 问题框架（1-2 段）
   引入原始来源，说明为什么这个信息值得关注。给出全文框架——「以下是 7 类最常见的无效投入」。

3. 逐条展开（核心，每条 2-5 段）
   每个分点用 `## N. 标题` 格式。
   每条的写法：
   - 先描述「这是什么坑」（让人对号入座）
   - 再给出原文的判断标准
   - 最后加**中国市场的对应分析**（百度/微信/国内工具 vs 国外差异）
   例子：Core Web Vitals 在谷歌是排名因素，在百度不是，所以国内站点的优化优先级完全不同。

4. 替代框架（2-4 段）
   不只说「别做什么」，还要说「那做什么」。提炼原文的正面框架（如 Pollitt 的三类标准），并用自己的话重组。

5. 升华/更大的图景（1-2 段）
   把话题放回趋势中——「AI 搜索正在改变发现路径」「SaaS 人头计费正在被 AI 侵蚀」。这一段的目的是让文章有层次，不止于「清单」。

6. 行动收尾（1 段）
   一句话让读者可以转发或执行。不要重复结论，而是给出判断。「这篇文章值得转发给你的开发同事——因为你省下了一句解释：'这个工单先不做了，它对业务没有可衡量的影响。'」
```

### 关键实践

**国外源本地化**（最重要）
- 原文基于 Google/海外环境 → 主动补充国内对应场景（百度、微信、抖音、小红书）
- 英文来源的策略：翻译 + 转述 + 本地化。保留原文核心论据，但替换例证为国内读者能感知的
- 例子：原文说「Google Search Console 显示正常就不用动」→ 补充「百度站长平台的对应功能是抓取诊断」

**文章长度控制**
- 每节不要展开过深——保持可读性，不要让读者觉得「太长不看」
- 每个分点 2-5 段为宜，够了就收

**语言风格**
- 遵循 c456-voice-journalist 声线（记者体，不是博客体）
- 比 Signal 稍口语化（公众号读者范围更广），但保持信息密度
- 不用感叹号、反问、网络梗、表情符号
- 段落短（手机阅读，3-5 句一段）

**品牌植入**
- 仅当话题与 c456 理念/产品有交集时自然提及
- 手法：用「类似 c456 一直关注的 X 方向」引出，不要用「我们早就说过」
- 不要每篇都提

### 参考格式

```markdown
# 主标题：提炼核心判断（可用冒号分隔观点与实际内容）

> 副标题或引言金句（可选，1 句概括核心）

## 场景锚定段（2-4 段）

## 1. 第一个分点

原文观点 + 中国市场分析 + 实操建议

## 2. 第二个分点

...

## 替代方案：不是只说不，而是说怎么做

## 写在最后

来源说明（附链接）
```

## §D 每日信息策展（Daily Curation）

每日信息采集与精选流程。由 cron 自动执行（每天早上 7:00），产出每日信号精选（草稿）并推送清单给用户。

### §D.0 策展哲学：不为信息而信息

c456 不是新闻媒体。策展的终极目的是 **为用户出可执行的方案**，不是报道行业动态。

### §D.01 来源多样化规则（2026-07-28 新增）

策展的 RSS 源按品类分为 A-G 七类（品类 G 专用于轨道 2 和轨道 3）。cron prompt 必须包含以下规则并用品类标注每条条目：

**强制规则：**
1. **每天至少覆盖 2 个不同品类**
2. **单个域名不超过 4 条**
3. 如果某个品类当天无合适信息，可以不选
4. 如果大部分内容来自同一品类，选该品类最有价值的 3-4 条，其余从其他品类补充

**品类分类：**
- **A — GEO / AI 搜索优化**：Search Engine Land、Moz、SEJ、Google Search Central、Perplexity
- **B — 品牌营销 / 内容策略**：CMI、HubSpot、Animalz、SparkToro、Neil Patel
- **C — AI 行业动态**：TechCrunch、VentureBeat、Ars Technica、Latent Space、Simon Willison、TLDR
- **D — 中国生态**：36kr（只取 AI/创业/品牌相关）、机器之心、sspai、ChineseSEO
- **E — 商业 / 策略**：SaaStr、DHH、Jason Fried、Smart Passive Income、GitHub Blog、LangChain
- **F — 工具发现**：Product Hunt（不定期）
- **G — 格局/储备**（需标注「轨道2」或「轨道3」）：不限来源，任何领域的信息，只要符合轨道 2（格局信号）或轨道 3（材料储备）的检验标准即可收录

**blogwatcher 失败时的 fallback 源（必须覆盖 ≥3 个品类）：** Search Engine Land、Content Marketing Institute、TechCrunch AI、Moz Blog、HubSpot Marketing、TLDR AI、36kr、Simon Willison。

**cron prompt 变动风险：** cron job 的 prompt 可能在另一会话中被覆盖。每次修改后应 `cronjob action='list'` 确认 `prompt_preview` 与写入的一致。参见 `references/daily-curation-cron.md` 的踩坑记录。

**⚠️ 禁止 [SILENT]**：策展 cron 的最终输出不能是 `[SILENT]`。如果当天没有值得策展的信息，也要输出一句说明。用户需要知道 cron 在正常运转。

### §D.02 三轨并行策展（2026-07-30 新增）

> 为了解决「信息面变窄」的问题，每日策展分为三条轨道。详见 `c456-curation-philosophy` §1.4。

**轨道 1：GEO/AIO 实操（核心轨道）**
- 检验标准：「能帮中小品牌直接动手做什么」
- 数量：5-8 条/天，必选
- 格式：现有完整格式（→ 价值 + 📌 可组合打法）
- 进入每日精选信号正文

**轨道 2：行业格局信号（可选）**
- 检验标准：「如果成立，我们之前的什么假设会变化」
- 数量：0-5 条/天
- 格式：不需要打法建议，写「值得关注的原因」和「挑战的假设」
- 以纯列表推送给用户，不进入信号正文

**轨道 3：材料储备（可选）**
- 检验标准：「能成为未来哪个主题的来源」
- 数量：0-3 条/天
- 只进 raw/素材库，不进信号

**推送格式：** 每日推送用分隔线分为三段（轨道 1 / 轨道 2 / 轨道 3）。

### §D.1 策展哲学

c456 不是新闻媒体。策展的终极目的是 **为用户出可执行的方案**，不是报道行业动态。

**核心检验（每条收录前必问）：**
```
1. 这个信息能帮目标用户出什么具体的方案？
2. 这个方案需要用户花多少钱/多少时间实施？
3. 用户看了方案后能直接动手做什么？
```
三条都答不出的信息不采。宁可每天 0 条，不凑 15 条没用的。

**打法三段论：**
```
信号（从信息中提取趋势） + 工具（具体产品/方法） → 打法（可执行的方案）
```

采集信息时，脑子里必须同时想两件事：
- 这条信息背后是什么**信号**？
- 这个信号可以和哪个**已有的工具/方法**结合，打出什么**打法**？

**GEO/AIO 方向（2026-07 更新）：**
策展的核心领域聚焦**中小品牌的 GEO/AIO（AI 搜索优化）**。每条信息必须能回答「这个信息能帮中小品牌做什么？」。客户画像从「小企业主/自由职业者」更新为「中小品牌负责人、市场运营人员、独立站站长」。详见参考文件中的 cron prompt 版本历史和品类分类。

**AISO（AI Search Optimization）方向：**
策展必须服务于「让目标用户在豆包/元宝/DeepSeek 等 AI 搜索中能找到你」这个终极目标。每条信息都要考虑：这个信息可以怎么转化成在 AI 引用的平台（公众号/知乎/百家号）上分发的内容。详见 `c456-strategy-creator` §7（AISO 模块）。

**客户画像驱动：** 策展前必须先有客户画像（产品/受众/目标/能力）。画像是动态的，每次迭代调整。画像采集使用 `c456-client-interview` 技能，策略生成使用 `c456-strategy-creator` 技能。

**技能自我进化：** 如果客户连续指出策展方向不对，**不是客户的问题，是你的筛选策略有问题**。不要问客户「要不要加新来源」——你是专家，你自己去判断哪里出了问题、需要加什么源、调什么权重，然后立即调整。详见 `c456-strategy-creator` §8（自我进化）。

详见 `c456-curation-philosophy` 技能（哲学层）。

### 双层信源策略

RSS 源分为两层，处理方式不同：

**Tier 1 — 权威源（直接作为内容来源）**
官方博客（GitHub/Google AI/LangChain/AWS 等）、科技媒体（TechCrunch/Ars Technica/VentureBeat/36kr/机器之心等）、arXiv 论文。
→ 这些源的条目可直接收录，内容作为引用来源。

**Tier 2 — 信号雷达（只检测热点，不直接引用）**
Hacker News、V2EX、Product Hunt、Indie Hackers、X/Twitter 转链。
→ 如果某个话题在这些源上出现热度（高票/高赞/多帖讨论），不要直接引用社区帖子本身。改为：搜索该话题的官方来源（官方博客、权威媒体报道），引用官方源。

### 来源质量优先级

按以下优先级选择引用来源：
1. **官方公告**（公司博客、官方新闻稿）— 最高优先级
2. **权威科技媒体**（TechCrunch/Ars/36kr/The Register 等）— 第二优先
3. **行业分析/深度博客**（Simon Willison/Pragmatic Engineer/SaaStr 等）— 第三优先
4. **X/Twitter 转链、社区讨论帖、V2EX/Reddit 帖子** — 仅当找不到官方源且内容本身有价值时才用，且需标注来源类型

### blogwatcher 运维

blogwatcher 数据库位于 `~/.blogwatcher-cli/blogwatcher-cli.db`（SQLite）。检查源是否正常：

```bash
# 检查 feed_url 缺失
sqlite3 ~/.blogwatcher-cli/blogwatcher-cli.db "SELECT id,name,feed_url FROM blogs WHERE feed_url IS NULL OR feed_url='';"

# 查看各源近期文章数
sqlite3 ~/.blogwatcher-cli/blogwatcher-cli.db "SELECT b.name,COUNT(a.id) FROM articles a JOIN blogs b ON a.blog_id=b.id WHERE a.published_date>='7天前日期' GROUP BY b.name ORDER BY COUNT(a.id) DESC;"

# 新增源
sqlite3 ~/.blogwatcher-cli/blogwatcher-cli.db "INSERT INTO blogs (name,url,feed_url) VALUES ('名称','首页URL','RSS URL');"
```

常见问题：**feed_url 为空时 blogwatcher 无法抓取 RSS 内容**（它会尝试 scrape 首页 HTML 但产出通常为零）。新增源或发现某源长期无产出时，首先检查 feed_url 是否正确设置。

### 常见错误

| 错误做法 | 正确做法 |
|---------|---------|
| 一篇博客发多条信号 | 每日只建一条 |
| 忘记 `--description` 参数 | 卡片描述从正文截断，显示不友好 |
| 未阅读原文就写简介 | 内容空洞，被用户退回 |
| 凑满 15 条，不管有没有用 | 宁可 0 条，不凑数 |
| 向客户「要不要加这个源」 | 你是专家，自己判断调整 |
| 写行业价值而不是客户价值 | 每条 `→ 价值：` 从目标客户角度写
| 最终输出 `[SILENT]` | 永远有输出——没内容也要告知用户今日无匹配信号 |
| blogwatcher 失败就停下 | 用 `curl -sL` 直接抓取关键源（Search Engine Land / TechCrunch / Moz / TLDR / 36kr / CMI / HubSpot / Simon Willison）|
| **来源单一化** | 所有条目来自同一域名 → 强制按品类分类选源，每天 ≥2 品类，单域名 ≤4 条 |
| **cron prompt 被意外覆盖** | cron job 的 prompt 可能在另一会话中被覆盖。修改后必须 `cronjob action='list'` 确认 `prompt_preview` 正确 |

## 完整内容生产工作流

### 前提：客户画像

在开始任何策展之前，必须先有客户画像。使用 `c456-client-interview` 采访客户，输出标准画像 JSON。然后使用 `c456-strategy-creator` 基于画像生成定制策展策略。

```
① 采访客户 → 输出画像（产品/受众/目标/能力）
② 生成策略 → 关键词/渠道/筛选规则/打法方向
③ 部署 cron → 每天按定制策略自动跑策展
④ 每天推送 → 用户从清单中选要写的条目
⑤ 深度写稿 → 选一篇深读、扩展、写稿
⑥ 发布 → screenshot + signal new + update --publish
⑦ 迭代 → 根据用户反馈调整策略
```

### 从每日选题到公开发布

**第 0 步（执行任何写作前）：查重。** 参见 `references/intake-duplicate-check.md`。用户说「收录 XXX」时先确认不重复再动手。

当从每日选题中选定一篇要写时，按以下顺序执行：

```
① 确认任务范围 → 是只发信号，还是信号+公众号长文？
   - 「可以发」→ 只执行步骤 ②→③→④→⑤→⑥→⑦（写信号并发布）
   - 「写篇公众号文章」→ 增加步骤 ⑧（在信号发布后，按 §E 写公众号长文）
② 定位类型 → 选择 §A/B/C 对应模式（如需公众号长文，额外参考 §E）
③ 加载 c456-voice-journalist → 应用记者声线规则
④ 阅读原文全文 → 提取至少 3 个具体数据点/引语
⑤ 按对应模式直接撰写最终稿（不经过大纲/初稿环节）
⑥ 运行 §6 自检清单（c456-voice-journalist）和 §3 自检清单（c456-sync）
⑦ 提交给用户审稿
⑧ 用户 OK → 用 c456-publish 发布上线
⑨ （如需要公众号版）信号发布后，按 §E 六段式结构写公众号长文，附来源说明
```

**重要：不要出大纲让用户确认。** 普通用户没有专业判断力也没有耐心判断大纲好坏。以结果为导向，直接写最终稿。用户审一次，成则发，不成改。没有「初稿先看看方向对不对」这个环节。

- 结构由本技能提供，声线由 `c456-voice-journalist` 提供，格式由 `c456-sync` 提供
- 三种配套技能必须同时加载，缺一不可
