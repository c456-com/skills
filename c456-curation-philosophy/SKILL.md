# c456 策思路方法论

> 哲学层技能。回答「为什么采集」和「采来做什么」的问题。是所有策展行为的上层指导原则。

---

## §1 核心原则

### 1.1 不为信息而信息

c456 不是新闻媒体，不需要报道每一条行业动态。**信息采集的唯一目的是为用户产出可执行的方案。**

一条信息值不值得收录，只问三个问题：

1. **这个信息能帮用户解决什么具体问题？**
2. **这个信息可以和哪个已有工具/方法组合，产生一个打法？**
3. **用户看了这个打法后能直接动手做什么？**

三条都答「不」 → 这条信息不采。

### 1.2 打法三段论

c456 的内容生产遵循一个公式：

```
信号（洞察） + 工具（能力） → 打法（可执行的方案）
```

| 环节 | 定义 | 举例 |
|------|------|------|
| **信号** | 从信息中提取的趋势性判断 | 「AI 入门门槛极低」「大模型价格暴跌」 |
| **工具** | 具体产品/技术/方法 | Hermes Agent、DeepSeek V4 Flash |
| **打法** | 信号 + 工具 组合成的可执行方案 | 「用 Hermes + DeepSeek 做营销自动化」 |

采集信息时，脑子里必须同时想两件事：
- 这条信息背后是什么**信号**？
- 这个信号可以和哪个**工具**结合，打出什么**打法**？

### 1.3 用户价值是唯一检验标准

每采集一条信息，都要能回答：**「这个对我的目标用户有什么实际价值？」**

价值不是「让用户知道这件事」，而是「让用户知道之后能做什么」。

### 1.4 四轨并行策展（2026-09-12 起）

> 单一检验标准导致信息面变窄。四条轨道分别回答四个不同的问题，每天并行出稿。
>
> 变更历史：2026-07-30 引入三轨（GEO 实操为核心）；2026-09-12 升为四轨——辉哥明确要求「每天知道 AI 圈的大事、新鲜事，以及有什么好的开源项目或产品出来」，因此把 AI 大事与开源/产品发现提为独立主干轨道，GEO 实操降为保底轨道（仍必选，但条数下调）。

#### 轨道 A：AI 大事 & 新鲜事（主干，必选）

- **检验标准**：「这条消息会不会改变从业者对 AI 的判断，或者今天圈内真的在讨论它？」
- **条数**：3-5 条/天
- **来源**：Hacker News 首页高票、TLDR AI、TechCrunch / VentureBeat / The Register AI、36kr、厂商官方博客（Anthropic / OpenAI / Google / Microsoft）
- **格式**：标题链接 + 类型 + 2-3 句含具体数字/版本号/金额的事实摘要 + 来源 + → 影响

#### 轨道 B：开源项目 & 新产品（主干，必选）

- **检验标准**：「这是能上手用、或值得看一眼的真东西吗？」（营销页、空壳 README 不算）
- **条数**：3-5 条/天
- **来源**：GitHub 新项目（近 7 天创建按 star）、GitHub 热门 AI/LLM/Agent 项目、Show HN、Product Hunt
- **格式**：`[项目名](URL) — 语言 / ⭐star` + 一句话解决的问题 + 谁在做 + 现状 + → 可用性（与 c456 客户方案/内容选题的关系，没有就写「暂无直接关联」）

#### 轨道 C：GEO/AIO 实操（保底，必选）

- **检验标准**：「这个信息能帮中小品牌直接动手做什么？」
- **条数**：2-3 条/天（下限降低，但不可空缺）
- **来源**：Search Engine Land / Moz Blog / Search Engine Journal / Google Search Central 及品类 B-E
- **格式**：保持原格式（→ 价值 + 📌 可组合打法 + 品类标注）

#### 轨道 D：材料储备（可选）

- **检验标准**：「这个素材能成为未来哪个主题的来源？」
- **条数**：0-3 条/天
- **格式**：`- [标题](URL) — 一句话为什么留`，不展开
- **不进入简报正文的信号化处理**，只记入素材库

#### 四条轨道的权重关系

```
轨道 A（AI 大事） ：必选 3-5 条，主干
轨道 B（开源/产品）：必选 3-5 条，主干
轨道 C（GEO 实操） ：必选 2-3 条，保底
轨道 D（素材储备） ：可选 0-3 条，只入库
```

#### 推送格式

用分隔线分四段，让辉哥一眼看出层次：

```
# c456 每日 AI 简报 | YYYY-MM-DD

--- 轨道 A：AI 大事 & 新鲜事 ---
（3-5 条）

--- 轨道 B：开源 & 新产品 ---
（3-5 条）

--- 轨道 C：GEO/AIO 实操 ---
（2-3 条）

--- 轨道 D：素材储备 ---
（0-3 条，仅标题 + 一句话）
```

**执行载体**：cron 任务 `c456-daily-brief`（每天 07:00 CST），采集层为 `~/.hermes/profiles/hermes-c456/scripts/ai-radar.py`（HN + GitHub + RSS，stdlib-only，stdout 注入 agent prompt），选稿与写作由 agent 完成，简报归档到 `c456-com/daily/briefs/YYYY-MM-DD-ai-brief.md`。

## §2 信息分层

所有采集来源分三个层级，处理方式不同：

| 层级 | 角色 | 处理方式 |
|------|------|---------|
| **Signal 信号层** | 发现趋势/机会/变化 | 提取信号→思考能组合成什么打法 |
| **Tool 工具层** | 发现具体可用工具 | 深度调研→确认能用在哪类打法中 |
| **Playbook 打法层** | 产出最终方案 | 信号+工具→写成可执行的步骤 |

### 2.1 信号层（Signal-Tier）

**来源：** RSS 中的科技媒体、官方博客、趋势分析、社区热帖

**采集动作：**
- 提取核心判断（不是转述新闻，是提炼趋势）
- 问：这个信号可以和哪个已知工具组合？
- 打标签：关联已有工具/方法

**输出：** 每天 ≤20 条精炼信号，附带「打法组合建议」

### 2.3 工具层（Tool-Tier）

**来源：** Product Hunt、GitHub Trending、官方发布、深度评测、技术博客、大V/自媒体研究者分享

**工具发现渠道：**

| 渠道类型 | 来源 | 用途 |
|---------|------|------|
| **产品发现** | Product Hunt、Hacker News Show、GitHub Trending | 发现新工具 |
| **大V/自媒体** | 技术博主、YouTuber、独立研究者 | 学习别人的方案和工作流 |
| **评测/对比** | 深度评测文章、社区讨论 | 了解工具的真实能力和局限 |

**采集动作：**
- 调研产品的核心能力、定价、局限
- 问：这个工具解决什么问题？可以和哪个信号组合？
- 建立工具与信号的关联索引

**输出：** 每周 3-5 个工具调研，标注「可用于什么打法」

### 2.4 生态聚焦层（Ecosystem-Tier）

c456 的方案交付依赖特定的工具底座，因此必须持续关注社区如何实际使用这些工具。

**当前核心底座：Hermes Agent**
- Hermes 是 c456 方案交付的默认自动化引擎
- 关注点不是 Hermes 发布了什么版本，而是**社区拿 Hermes 做了什么**
- 别人的用法、组合、脚本、技能 → 可以直接复用到 c456 的客户方案中

**关注什么：**
| 关注内容 | 为什么 | 从哪里找 |
|---------|--------|---------|
| 别人用 Hermes 做的自动化工作流 | 可以直接复制给客户 | Twitter/Reddit/V2EX/博客 |
| 开源的 Hermes 技能和脚本 | 降低 c456 的开发成本 | GitHub/社区分享 |
| Hermes + 其他工具的组合方案 | 启发 c456 的新服务设计 | 技术博客/播客/教程 |
| 使用中遇到的坑和解决方案 | 避免 c456 踩同样的坑 | 社区讨论/Issues/Discord |

**评估标准：**
- 这个用法能直接或改造后给 c456 的客户用吗？
- 这个组合方案比我们现在的方案更好吗？
- 这个用法提示了哪些我们没想到的场景？

### 2.5 打法层（Playbook-Tier）

**来源：** 信号+工具的组合产物

**生产动作：**
- 选取一个信号 + 一个工具
- 思考目标用户的真实场景
- 写成步骤化的可执行方案

**输出：** 每月 2-4 篇打法文章（playbook）

## §3 用户画像驱动采集

每次信息采集前，必须明确当前服务的用户画像。画像包含以下维度：

| 维度 | 问题 | 示例 |
|------|------|------|
| **产品/服务** | 用户卖什么？ | AI 营销自动化工具 |
| **目标用户** | 用户想影响谁？ | 独立开发者、SaaS 创始人 |
| **终极目的** | 用户想达到什么？ | 降低获客成本，提高转化率 |
| **地域** | 用户在哪个市场？ | 中文市场 / 英文市场 |
| **内容渠道** | 用户发在哪？ | 公众号 / 知乎 / Twitter |
| **能力边界** | 用户自己能做到什么程度？ | 会写代码 / 不会写代码 |

画像是动态的——每次对话更新，采集策略随之调整。

## §4 记者采访模式

信息采集不是「机器扫 RSS」，而是 **「记者采访客户 → 理解需求 → 定制采集」**。

标准流程：

```
① 采访客户 → 建立画像（产品/受众/目的/地域）
② 设计采集策略 → 关键词/渠道/来源/筛选规则
③ 执行采集 → 按策略从多个渠道获取信息
④ 筛选组合 → 提取信号，关联工具，提出打法建议
⑤ 推送 → 给客户看，问「哪个打法值得写？」
⑥ 迭代 → 根据反馈调整采集策略
```

每次迭代都让画像更精准，采集更聚焦。

## §5 质量检验清单

**§5.1（GEO 轨道 C 专用）** 每条采集到的信息，在纳入 GEO 轨道前必须通过以下检验：

- [ ] 这条信息指向什么**信号**？（趋势/机会/变化）
- [ ] 这个信号可以和哪个**已有工具/方法**组合？
- [ ] 组合后能产出什么**具体的打法**？
- [ ] 这个打法的目标**用户是谁**？（与画像匹配吗？）
- [ ] 用户看了之后**能直接动手做什么**？
- [ ] 如果今天不采这条，用户会**损失什么实际价值**？

**不满足 ≥4 条 → 不采。**

**§5.2（AI 大事 / 开源与新产品轨道 A、B）** 这两条轨道服务的是「认知更新」而不是「出方案」，检验标准不同——不要用 §5.1 去卡它们：

- 轨道 A：① 有具体数字/版本号/金额/人名；② 出自可核实的原始来源（官方博客、一手报道）；③ 今天圈内真的在讨论它。三条中至少满足 2 条。
- 轨道 B：① 代码真的能跑或产品真的能用（有 release / 在线地址 / 安装命令）；② 有明确的「解决什么问题」；③ star 或讨论量能说明它在被真实使用。三条中至少满足 2 条。

**反过来，轨道 A/B 不适用「能帮客户出什么方案」这个门槛**——这是 2026-09-12 三轨升四轨的核心修正：如果继续用 GEO 出方案的标准卡 AI 大事，信息面会被卡死，辉哥要的「新鲜事」永远进不来。

## §7 GEO/AISO — Generative Engine Optimization & AI Search Optimization

策展的最终目的不仅是「出方案」，还要帮品牌出现在 AI 搜索的结果中。这包含两个互补维度：**GEO（Generative Engine Optimization）** 和 **AISO（AI Search Optimization）**。

| 维度 | 焦点 | 核心问题 |
|------|------|---------|
| **GEO** | 品牌在 AI 搜索中的可发现性 | AI（豆包/元宝/DeepSeek/ChatGPT/Perplexity）能否正确识别你的品牌？ |
| **AISO** | 内容在 AI 引用源中的分布 | 你的内容是否出现在 AI 训练数据/引用源中？ |

### 7.1 核心理念

用户不再通过搜索引擎找解决方案，而是直接在 AI 提问。AI 的回答引用哪些来源、识别哪些品牌信号，决定了哪些企业能被推荐。

**c456 的双层策略：**
1. **GEO 层** — 帮品牌建设 AI 可识别的信号（结构化数据、实体标注、品牌一致性、llms.txt、Schema.org）
2. **AISO 层** — 在 AI 引用的平台上发布内容（公众号/知乎/百家号/头条号），让 AI 在回答时引用

### 7.2 品牌在 AI 中的可见性矩阵

| 问题 | 指标 | 检查方法 |
|------|------|---------|
| AI 能正确描述品牌吗？ | 品牌名称/Logo/简介的 AI 识别一致率 | 在豆包/元宝/DeepSeek 中提问「XX 是什么」 |
| AI 能找到品牌官网吗？ | 搜索结果中的域名准确性 | 在 ChatGPT/Perplexity 中提问「XX 官网」 |
| AI 能验证品牌资质吗？ | 实体信息准确率（地址/联系方式/服务范围） | 使用结构化数据测试工具 |
| 品牌内容是否被 AI 引用？ | 在 AI 回答中出现的内容片段 | 分析 AI 回答中的引用来源 |

### 7.3 策展时的 GEO/AIO 维度

每条采集的信息都要回答：
- 这条信息对中小品牌的 **GEO 有什么指导意义**？（结构/信号/引用机制）
- 这个工具/方法能帮品牌 **提升在 AI 搜索中的可见度** 吗？
- 这个趋势意味着品牌需要 **调整什么信号资产**？

### 7.4 多品类品牌在 AI 中的可见度策略（重要）

真实的企业往往有多个产品或服务线。GEO 的目标不是让企业砍掉赚钱的业务，而是**结构化多品类布局**。

**问题：** 当一个网站同时宣传多个品类时（如「建站+小程序+推广+视频」），AI 无法将其归类到任何一个品类，结果就是在所有品类中都不会被推荐。

**解决方案不是砍品类，是结构化多品类：**
1. 首页做「伞形品类」——定位为「XX 服务提供商」，作为公司总入口
2. 每个服务建独立落地页——建站一个页面、小程序一个页面、推广一个页面
3. 各自做 llms.txt 条目——每个服务在 llms.txt 中作为独立 section
4. 各自做 Schema——不同服务用对应的 Schema 类型
5. 各自做内容——每个落地页只讲自己的话题，不混杂

这样 AI 搜索不同的品类时，都能找到对应的落地页，互不干扰。

**已验证的对比案例：**
- baklib.com（首页伞形 + 每个场景独立页面）= ✅ 正确做法
- sobaking.com（所有品类混在首页）= ❌ 错误做法

详见测评报告。

### 7.5 打法方向（策展组合时参考）

- **GEO 实操指南**：在 AI 搜索中提升品牌可见性的具体方法
- **AI 搜索平台拆解**：豆包/元宝/DeepSeek/ChatGPT 各自引用什么来源、怎么被收录
- **品牌信号建设**：中小品牌如何在 AI 时代建立可被识别的一致性品牌信号
- **零成本品牌曝光**：不花钱的内容策略、社区运营、口碑传播
- **内容被 AI 引用的技巧**：结构化数据、实体标注、可引用格式
- **中国 AI 平台生态**：中文 AI 搜索对品牌发现的特殊规则

详见 `c456-strategy-creator` §7（AISO 模块）和 `references/daily-curation-sources-v5.md`（GEO/AIO 策展 RSS 源列表）。

## §8 AI 平台作为调研对象

> 策展的信息源不仅是 RSS 和网页——**AI 平台本身也是重要的调研对象**。向多个 AI 平台问同一个问题，收集它们怎么回答、引用了什么来源，从中提取共识、差异和独特洞察。

### 8.1 为什么要把 AI 平台当调研对象

传统调研是「人找信息」——人从网页、社区、报告中找答案。
AI 平台调研是「信息找人」——你把问题抛给 AI，看它从训练数据和联网检索中拉出了什么信息。

| 维度 | 传统调研 | AI 平台调研 |
|------|---------|------------|
| 信息来源 | 网页/社区/报告 | AI 的训练数据 + 实时检索结果 |
| 覆盖范围 | 逐页查看，可能遗漏 | AI 替你综合了海量信源 |
| 偏差 | 覆盖偏差（你没搜到的就错过） | AI 的检索偏好 + 训练偏差 |
| 独特价值 | 你控制信源选择 | **你看 AI 怎么理解你的话题** |

AI 平台调研的核心价值不是「问 AI 答案对不对」——而是 **「了解 AI 怎么看你的话题」**。这在 GEO 优化中尤其重要：诊断品牌在 AI 中的认知状态。

### 8.2 多 AI 平台调研方法论

#### 核心原则

**不要只看一个 AI 的回答。** 不同平台的训练数据、检索源、重排策略各不相同，单平台回答不可信。必须对比至少 3-5 个平台。

#### 标准化流程

```
① 设计调研问题（1 个核心问题，足够开放让 AI 展示知识）
② 逐个向目标 AI 平台提问
③ 对每个回答做标准化记录（见模板）
④ 跨平台交叉分析
⑤ 提取共识、分歧、独特洞察
⑥ 合成为策略建议
```

#### 问题设计原则

- 问题要**足够开放**——让 AI 有机会展示它知道什么，不只是「是/否」或搜索摘要
- 问题要**中性**——不要引导 AI 往某个方向回答
- 问题要**行业相关**——和你要研究的领域直接相关
- 一次只问一个核心问题——避免复合问题导致 AI 部分回答

#### 标准化记录字段

每条回答必须记录以下维度（见模板文件）：

| 字段 | 说明 | 示例 |
|------|------|------|
| platform | 平台名称 | DeepSeek |
| query_time | 提问时间 | 2026-07-29 |
| login_required | 是否需要登录 | 否 / 手机号 / 微信扫码 |
| web_search | 是否启用联网搜索 | 是 / 否 / 未说明 |
| answer_full_text | 答案原文（完整复制） | ... |
| citations | 引用来源列表 | URLs |
| behavior_notes | 行为观察 | 见注 |

**行为观察字段**记录：回答速度、引用格式、追问建议、语气/结构/商业话术/过度承诺/整体倾向。

#### 跨平台分析框架

| 分析维度 | 问什么 | 价值 |
|---------|--------|------|
| **共识** | 所有平台一致认同的观点 | ⭐⭐⭐⭐⭐ 强信号 |
| **分歧** | 平台间立场/观点不一致 | ⭐⭐⭐⭐ 关键 |
| **独特洞察** | 某个平台独有的观点或数据 | ⭐⭐⭐ 需验证 |
| **引用来源** | 不同平台引用了哪些来源 | ⭐⭐⭐⭐⭐ 最核心 |
| **立场倾向** | 平台偏向某个立场或技术方案 | ⭐⭐⭐ 平台知识偏好 |
| **立场分类** | 将各平台归入策略派别（API驱动派/私有RAG派/内容布局派/信源建设派等） | ⭐⭐⭐⭐⭐ 合成策略时最关键维度 |
| **语气/风格** | 助手风格还是客观分析 | ⭐⭐ 角色定位 |

#### 合成策略建议

交叉分析后输出结构化策略文档。

### 8.3 适用场景

| 场景 | 为什么用 | 平台选择 |
|------|---------|---------|
| GEO 诊断 | 了解品牌在各 AI 中的当前认知状态 | 6 大国内 AI 全部覆盖 |
| 竞争分析 | 了解竞品在各 AI 中的提及率和引用源 | DeepSeek + Kimi + 通义 |
| 行业趋势 | 了解 AI 如何理解当前行业热点 | 任选 3-4 个平台 |
| 技术方案验证 | 看 AI 推荐什么方案、引用了谁 | DeepSeek + 元宝 |
| 内容策略研究 | 了解什么信源被 AI 高频引用 | 全部平台 |

### 8.4 重要警示

| 警示 | 说明 |
|------|------|
| AI 在编造 | AI 可能在回答中编造来源 URL 或事实——始终验证引用 URL 是否真实 |
| 非确定性回答 | 同一问题在不同时间问结果可能不同——重要结论隔天复测 |
| 平台偏差 | 豆包偏向字节生态信源，元宝偏向微信生态——理解偏差再解读 |
| 不把 API 当优化手段 | 反复用 API 不会让 AI 记住品牌——API 是监测工具不是优化工具 |
| 单次不可靠 | 同一平台回答可能变化——做 3 次取平均或最常见模式 |
| **平台生态自推** | 平台倾向于推荐自家生态的解决方案（豆包→字节/头条、元宝→微信、文心→百度、通义→阿里）——分析时要识别生态偏好 vs 客观推荐 |
| **匹配用户规模** | 用户要的是每天问几个问题让 AI 逐渐了解品牌，不是分布式爬虫系统。不要提供超出需求一个数量级的方案 |

### 8.5 与 §7 GEO/AISO 的关系

§7 品牌建设（让 AI 发现品牌）+ §8 调研诊断（了解 AI 对品牌的当前认知）= 闭环：建设 → 诊断 → 调整建设方向。

详见 `references/multi-ai-platform-collection-template.md`（结构化采集模板）。

## §9 技能自我进化

### 9.1 筛选策略自检

如果客户说「这消息没用」或连续拒绝推送，**不是客户的问题**。检查：
1. 来源是否匹配画像？→ 调来源
2. 关键词是否过时？→ 更新关键词
3. 筛选规则是否太宽/太窄？→ 调阈值
4. 客户画像是否已经变化？→ 通知客户重新采访

不问客户「要不要加这个源」——你是专家，自己判断调整。

### 9.2 框架级自检（2026-07-30 新增）

如果按以上检查调整后，客户仍反馈「信息面变窄」「同质化」「整天看到一样的内容」——**问题不在筛选规则，在策展框架本身**。

此时检查：

1. **当前在运行几条轨道？** 少于 3 条 → 打开轨道 D 或补足 B（AI 大事/开源产品是最容易被 GEO 视角挤掉的）
2. **轨道 2 的格局信号是否覆盖了品类之外的来源？** 从 A-F 之外的世界找信号
3. **轨道 3 的素材库是否有超过 2 周没更新的主题？** 表明筛选规则可能太死
4. **最近一次真正「意外」的信息是什么时候出现的？** 太久没有 → 需要放宽其中一条轨道的边界

**一句话触发规则**：当用户说出「信息面越来越窄」「怎么都是这些」「我们漏了什么」——立即启动框架级自检，而不是继续调整筛选规则。

### 9.3 品类分类自检

品类分类（A-F）不是固定的。如果某个品类连续 2 周产出低于预期（平均每周 <1 条有价值的条目）：
1. 检查该品类的源是否还在更新（feed_url 是否失效）
2. 检查该品类的选题方向是否和当前画像匹配
3. 如果都不匹配 → 停用该品类，不再设为强制覆盖目标
